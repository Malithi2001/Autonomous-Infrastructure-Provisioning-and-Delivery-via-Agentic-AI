# Evaluation Plan

This document defines how to evaluate the final-year project MVP:

`Agentic AI-Powered Smart DevOps Assistant for Autonomous Software Delivery and Infrastructure Management`

## Evaluation Objectives

The evaluation measures whether the system improves common CI/CD workflows compared with manual developer effort.

Primary objectives:

- Measure CI/CD failure classification quality.
- Compare manual and automated workflow setup time.
- Compare manual and assisted failure diagnosis time.
- Measure fix recommendation usefulness and safe fix PR success rate.
- Verify safety controls through approval and audit logging tests.

## Model Metrics

Use the trained model reports generated by:

```bash
cd backend
venv/bin/python app/ml/train_failure_model.py
```

Artifacts:

- `backend/app/ml/reports/metrics.json`
- `backend/app/ml/reports/classification_report.txt`
- `backend/app/ml/reports/confusion_matrix.png`

Metrics to report:

- Accuracy
- Macro precision
- Macro recall
- Macro F1-score
- Weighted precision
- Weighted recall
- Weighted F1-score
- Per-label precision/recall/F1
- Confusion matrix

Labels:

- `npm_missing_lockfile`
- `npm_missing_test_script`
- `npm_install_failed`
- `npm_build_failed`
- `python_missing_dependency`
- `pytest_not_found`
- `module_not_found`
- `maven_test_failed`
- `docker_build_failed`
- `wrong_runtime_version`
- `unknown_failure`

Suggested acceptance target for MVP:

- Overall accuracy: at least 80% on the curated test split.
- Macro F1-score: at least 75%.
- No critical class should have zero recall unless the class has too few samples for reliable splitting.

## Manual vs Automated CI/CD Setup Time

### Goal

Measure whether repository scanning and workflow generation reduce setup time for a basic CI workflow.

### Test Setup

Use 3 to 5 demo repositories or file-list scenarios:

- Node.js / React
- Python / FastAPI
- Java / Maven
- Docker-based project
- Unknown or mixed project

### Manual Baseline

For each repository, ask a participant or evaluator to:

1. Inspect repository files.
2. Identify language/framework/package manager.
3. Choose a CI workflow structure.
4. Write a GitHub Actions workflow file.
5. Save the workflow path.

Record:

- Time taken in seconds/minutes.
- Number of mistakes found in YAML.
- Whether the workflow matches the stack.

### Automated Flow

For each repository:

1. Use Repository Setup page.
2. Enter `owner/repo`.
3. Click `Scan Repository`.
4. Click `Create Workflow PR`.

Record:

- Time to detected stack.
- Time to generated workflow PR.
- Whether stack detection is correct.
- Whether generated YAML is valid.
- Whether PR branch/path are correct.

### Metrics

- Average manual setup time.
- Average automated setup time.
- Percentage time reduction.
- Stack detection accuracy.
- Workflow YAML validity rate.
- Workflow PR creation success rate.

Example table:

| Scenario | Manual time | Automated time | Time saved | Stack correct | YAML valid | PR created |
| --- | ---: | ---: | ---: | --- | --- | --- |
| React/npm | 8 min | 45 sec | 90.6% | Yes | Yes | Yes |
| FastAPI | 7 min | 50 sec | 88.1% | Yes | Yes | Yes |

## Failure Diagnosis Time

### Goal

Measure whether the assistant reduces the time needed to identify a CI/CD failure root cause.

### Test Scenarios

Use representative failed logs:

1. Missing npm test script.
2. Missing npm lockfile.
3. Python dependency missing.
4. Pytest command not found.
5. Maven test failure.
6. Docker build failure.
7. Wrong runtime version.
8. Unknown failure.

### Manual Baseline

For each log, ask evaluator to:

1. Read the log.
2. Identify the failure category.
3. Suggest a fix.

Record:

- Time to diagnosis.
- Correct/incorrect label.
- Quality of suggested fix.

### Automated Flow

For each log:

1. Open CI/CD Assistant.
2. Paste log.
3. Click `Predict Failure`.
4. Record label, confidence, suggested fix.

Record:

- Time to prediction.
- Correct/incorrect label.
- Whether suggested fix is useful.
- Whether risk level is appropriate.

### Metrics

- Average manual diagnosis time.
- Average automated diagnosis time.
- Diagnosis time reduction.
- Prediction accuracy on scenario set.
- Suggested fix usefulness rate.

Suggested usefulness scoring:

- 2 = directly useful and actionable.
- 1 = partially useful but needs manual interpretation.
- 0 = not useful or misleading.

## Fix Recommendation Success Rate

### Goal

Measure whether recommendations are safe, understandable, and appropriate for the predicted label.

### Supported Safe Recommendation Labels

- `npm_missing_test_script`
- `npm_missing_lockfile`
- `pytest_not_found`
- `python_missing_dependency`
- `wrong_runtime_version`
- `docker_build_failed`

### Metrics

- Recommendation generated: yes/no.
- Correct root cause explanation: yes/no.
- Safe fix available flag correct: yes/no.
- Risk level correct: low/medium/high.
- Requires approval flag correct: yes/no.
- Recommended changes are understandable: score 0-2.

Example table:

| Label | Root cause correct | Safe fix flag correct | Risk correct | Approval correct | Notes |
| --- | --- | --- | --- | --- | --- |
| npm_missing_test_script | Yes | Yes | Yes | Yes | Low-risk workflow command change |
| wrong_runtime_version | Yes | Yes/Partial | Medium | Yes | Should avoid uncertain runtime edits |

## Safe Fix PR Success Rate

### Goal

Evaluate whether low-risk fix PR generation works without unsafe direct commits.

### Supported First Fixes

- `npm_missing_test_script`
- `npm_missing_lockfile`
- `pytest_not_found`

### Test Method

For each supported label:

1. Create or seed a workflow failure record.
2. Ensure repository has a matching workflow file pattern.
3. Click `Create Fix PR`.
4. Inspect created PR.

Expected:

- New branch is created.
- No direct commit is made to `main` or `master`.
- Only workflow file is changed.
- PR title and body explain the reason.
- WorkflowFailure record is updated with `fix_pr_url`.
- Audit entry is created.

Metrics:

- Fix PR creation success rate.
- Correct branch naming rate.
- Correct file patch rate.
- No-direct-main-commit compliance.
- Audit logging success rate.

## Human Approval Evaluation

### Goal

Confirm medium/high-risk actions are gated before repository modification.

### Test Method

1. Use or seed a workflow failure with medium/high-risk recommendation.
2. Click `Create Fix PR`.
3. Confirm status becomes approval required/pending.
4. Open Approvals page.
5. Review approval details.
6. Approve the request.
7. Confirm fix PR creation continues.
8. Repeat with rejection.

Expected approval details:

- Repository.
- Workflow run.
- Predicted failure.
- Suggested fix.
- Proposed file changes.
- Risk level.

Metrics:

- Approval created for medium/high-risk actions: yes/no.
- No PR before approval: yes/no.
- Approval resumes action correctly: yes/no.
- Rejection prevents action: yes/no.
- Audit logs approval decision: yes/no.

## Audit Logging Evaluation

### Goal

Verify important actions are recorded without exposing secrets.

Actions to verify:

- Model prediction.
- Repository scan.
- Workflow generation.
- Workflow PR creation.
- Workflow failure webhook.
- GitHub log download.
- Fix recommendation.
- Fix PR creation.
- Approval decision.

Checks:

- Action name present.
- Tool name present.
- Input summary present.
- Output summary present.
- Status present.
- Actor/user present where available.
- Timestamp present.
- Secrets/tokens are not logged.

API filter examples:

```bash
curl -i -sS -b /tmp/devops_demo_cookie.txt \
  "http://127.0.0.1:8000/api/v1/audit?limit=50&tool=github&status=success"
```
